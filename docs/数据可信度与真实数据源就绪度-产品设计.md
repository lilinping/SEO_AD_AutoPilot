# 数据可信度与真实数据源就绪度 — 产品设计

> 状态：设计草案 v0.1
> 关联缺陷：`KeywordResearchSkill` 曾在“有 Google Key、无 CX”时把合成估算标注为真实 Google 数据。
> 本文把这个点状修复上升为一个跨产品的通用能力，避免同类问题在其它 skill/connector 重复发生。

## 1. 背景与问题定义

项目的核心原则是「白帽、先预览后执行、可解释、可回滚」，其中最底层的一条隐含契约是：

> **绝不能把“看起来能用”当成“真的能用”，绝不能把合成/降级数据冒充成真实数据。**

当前实现里，大量能力在缺真实凭证时会静默退回 `synthetic` / `fallback`，而“是不是真实数据”这件事：

- 判定口径不统一：有的看“有没有 Key”，有的看引擎 `is_available()`，有的看证据新鲜度。
- 暴露方式不统一：keyword 用 `api_source` + `warnings`，connector 用 `providerMode` / `evidenceGapType`，视觉农场用 `readinessGapType`。
- 用户视角缺乏一个统一答案：**“我这份报告，到底有多少是真的？还差什么才能变真？”**

产品目标不是消灭合成数据（它对冷启动/演示有价值），而是让**真实度全程可见、可解释、可操作**。

## 2. 目标用户与核心诉求

| 角色 | 核心诉求 | 当前痛点 |
| --- | --- | --- |
| 独立站站长 | 想知道建议是否可信、值不值得照做 | 分不清报告是真实搜索数据还是模型估算 |
| 增长/运营负责人 | 交付客户前要确认数据源真实 | 缺一个“可信度总览”，只能逐页猜 |
| 技术团队 | 知道差哪个凭证、去哪补 | 报错/降级信息分散，配置指引不明确 |
| 服务商 | 对多个站点批量核查真实度 | 没有工作区级“真实度就绪度”视图 |

## 3. 产品原则

1. **默认标注来源**：任何对外输出的数据对象都带可信度标签，不允许“无标签”。
2. **降级必须显性**：一旦走 fallback/synthetic，必须有明确原因 + 补齐动作，而不是静默成功。
3. **部分配置视为未就绪**：凭证不完整（如 Key 无 CX）等同未接入真实源，不得标真实。
4. **可信度可聚合**：单条 → 报告 → 项目 → 工作区，逐级可汇总为一个就绪度分。
5. **每个缺口都可执行**：每个 gap 都要能回答“缺什么、卡在哪、下一步点哪里”。

## 4. 数据可信度模型（统一契约）

引入统一的 **DataProvenance（数据出处）** 标签，供所有 skill / connector / 报告复用。

```
DataProvenance:
  source_tier:   "real" | "partial" | "synthetic" | "unknown"
  provider:      str            # 如 google_custom_search / bing_web_search / dataforseo
  evidence_at:   datetime|null  # 最近一次真实命中时间
  is_fresh:      bool           # 是否在新鲜度窗口内
  gap_type:      str            # missing_credential / partial_credential / stale / provider_error / none
  gap_summary:   str            # 一句话人话解释
  remediation:   str            # 下一步动作（含指向的配置项/页面）
```

`source_tier` 定义：

| tier | 含义 | 触发条件 |
| --- | --- | --- |
| `real` | 真实源命中且新鲜 | 引擎 `is_available()` 为真 + 成功返回 + 未过期 |
| `partial` | 配置不完整或部分降级 | 例如 Google 有 Key 无 CX；部分关键词命中、部分降级 |
| `synthetic` | 完全由合成引擎产出 | 无任何可用真实源 |
| `unknown` | 状态不可判定 | 探测异常/超时且无历史证据 |

> 本次 keyword 修复正是这个模型的第一个落地点：`api_source=synthetic_fallback` + 明确 CX 缺失告警，对应 `source_tier=partial`、`gap_type=partial_credential`。

## 5. 功能需求

### 5.1 P0 — 统一可信度标签（后端契约）
- 新增共享 `DataProvenance` 模型（Python `models.py` + `packages/contracts`）。
- keyword / ecommerce / trend·news·qa / ad_network / search 等 skill 输出统一带 `provenance`。
- 判定一律以引擎/连接器真实 `is_available()` + 证据新鲜度为准，禁止“只看 Key”。

验收：任一 skill 在“凭证不全”场景下，`source_tier != real` 且带 `gap_type` 与 `remediation`。

### 5.2 P0 — 可信度就绪度接口
- 扩展既有 `GET /api/connectors/health` 与 `GET /api/product-benchmark`：补 `dataTrustScore`（0–100）与分 provider 的 `source_tier` 分布。
- 新增 `GET /api/data-trust`（工作区级）与 `GET /api/projects/{id}/data-trust`（项目级），聚合所有数据源的 tier、gap、remediation。
- 支持 `projectId` 过滤，与现有接口口径保持一致。

验收：一次调用即可回答“本项目真实数据覆盖率、还差哪些源、每个源下一步动作”。

### 5.3 P1 — 前端可信度展示
- **报告页角标**：每张报告卡片右上角显示 `真实 / 部分 / 合成` 徽章，hover 展示 gap 与补齐指引。
- **可信度总览面板**：并入 `/acceptance` 与项目详情，展示 dataTrustScore、tier 分布、按阻断度排序的补齐清单。
- **配置直达**：每个 gap 的补齐动作直接链接到 `/settings` 对应字段（如 Google CX 输入框）。

验收：用户只看一个页面即可判断“这份分析可信度”，并能一键跳到补齐入口。

### 5.4 P1 — 设置页凭证校验
- `/settings` 保存搜索/广告/发布凭证时做“完整性校验”：如填了 Google Key 未填 CX，即时提示“配置不完整，仍会走合成数据”。
- 提供“测试连接”按钮，返回 `source_tier` 实测结果。

### 5.5 P2 — 可信度纳入验收 Gate
- 新增 `data_trust_ready` gate：工作区级真实数据覆盖率达阈值方可通过。
- 与现有 `real_provider_samples`、`market_evidence_freshness` 对齐，避免重复判定。

## 6. 交互与文案规范

- 徽章文案：`真实数据` / `部分真实` / `合成估算` / `状态未知`。
- 合成场景固定话术模板：`当前为合成估算，原因：{gap_summary}。补齐方式：{remediation}。`
- 严禁使用“已接入/已就绪”等词描述 `partial` 或 `synthetic` 状态。

## 7. 指标

| 指标 | 说明 | 目标方向 |
| --- | --- | --- |
| 真实数据覆盖率 | `real` tier 数据源占比 | ↑ |
| 静默降级率 | 走 fallback 但未标注的比例 | → 0 |
| 可信度徽章曝光率 | 带 provenance 的输出占比 | → 100% |
| 凭证补齐转化率 | 看到 gap 后完成配置的比例 | ↑ |

## 8. 落地路线

| 阶段 | 范围 | 产出 |
| --- | --- | --- |
| 已完成 | keyword 源判定修复 + 回归测试 | 首个 `partial` 场景被正确标注 |
| P0-1 | `DataProvenance` 模型 + keyword/ecommerce/market 接入 | 后端统一契约 |
| P0-2 | `data-trust` 接口 + benchmark 扩展 | 就绪度可查询 |
| P1-1 | 报告角标 + 可信度面板 + 设置校验 | 用户可见可操作 |
| P2-1 | `data_trust_ready` gate | 纳入发布门禁 |

## 9. 非目标

- 不消灭合成数据（保留冷启动/演示用途）。
- 不在本期接入具体第三方付费数据商（DataForSEO/Ahrefs 等接入另列）。
- 不改变现有审批/回滚状态机语义。
