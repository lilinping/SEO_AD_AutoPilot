# SEO-AD AutoPilot 功能完善与验收说明

本文档面向项目维护者、产品负责人和后续接手的 Agent，说明当前 SEO-AD AutoPilot 相比成熟产品补齐后的能力范围、关键闭环、验收入口和仍需继续推进的方向。

## 1. 背景与目标

当前项目已经具备 SEO 分析、广告审计、内容策略、审批发布、回滚、监控告警、多 provider 接入、视觉回归、runtime edge、billing gateway 等主干能力。近期完善工作的重点不是继续堆叠新模块，而是把“功能是否真的可生产使用”转成可观测、可阻断、可修复的验收链路。

核心目标：

- 对比成熟产品能力，识别当前项目的生产化缺口。
- 把缺口落到 API、前端验收页和测试断言中，而不是停留在文字说明。
- 让每个关键模块都能回答三个问题：缺什么、卡在哪个 gate、下一步怎么修。

## 2. 成熟产品对标结论

本项目主要对标以下成熟产品能力类型：

| 能力方向 | 参考产品类型 | 成熟产品特征 | 当前项目补齐重点 |
| --- | --- | --- | --- |
| SEO 监控与内容治理 | Conductor、ContentKing、Botify | 持续抓取、真实搜索数据、内容机会与技术 SEO 闭环 | 强化真实 provider evidence、market evidence freshness、验收 gate |
| 合成监控与视觉回归 | Checkly、Percy、Chromatic | 定时探测、截图差异、失败定位、发布阻断 | 强化 visual farm readiness、probe freshness、run failure 诊断 |
| 边缘运行时与多站点路由 | Vercel、Cloudflare | host/path rewrite、canary、rollback、runtime probe | 已有 runtime route/edge probe/rollout history，后续继续补生产流量验证 |
| 广告平台报表 | Google Ad Manager、AdSense、Mediavine | RPM/eCPM、库存状态、结算窗口、异常收益追踪 | 已补 ad network evidence 与收益字段，后续扩大真实平台样本 |
| 商户结算与 payout | Stripe Connect、PayPal Payouts、Wise | 账户状态、结算执行、失败补偿、对账 ID | 已有 billing gateway 与 settlement history，后续补深度对账 |
| 实验治理 | Optimizely、LaunchDarkly | 分流历史、guardrail metric、自动停止、回滚联动 | 已有 policy/readiness/assignment，后续补指标闭环 |

结论：当前项目的主要差距不是“功能少”，而是“功能广但生产证据链不够硬”。因此本轮重点补了成熟度诊断、真实 provider 证据缺口、视觉农场生产化缺口和验收页展示。

## 3. 已补齐的核心能力

### 3.1 产品成熟度对标报告

新增或完善的接口：

- `GET /api/product-benchmark`
- `GET /api/product-benchmark/remaining`

能力说明：

- 将 provider、视觉农场、runtime edge、广告回传、结算网关、实验治理等能力拆成成熟度评分。
- 每项能力按五段流程诊断：`intake`、`evidence`、`execution`、`verification`、`automation`。
- 自动标记每项能力的最弱阶段：`weakestStageId`、`weakestStageTitle`。
- 将成熟度缺口转成 remaining task，便于后续按阻断程度继续修复。

### 3.2 真实 Provider 证据缺口诊断

增强的接口：

- `GET /api/connectors/health`

新增字段位于 `providerCoverage` 每一项中：

- `evidenceGapType`
- `evidenceGapSummary`
- `smokeAction`
- `smokeActionPath`
- `smokeActionLabel`
- `acceptanceGateId`

缺口类型：

| 类型 | 含义 | 处理建议 |
| --- | --- | --- |
| `missing_real` | 没有真实 provider 样本 | 配置凭证并执行 provider smoke |
| `fallback_only` | 只有 fallback/synthetic 数据 | 替换为真实 API 或真实写回样本 |
| `strict_gap` | 有连接但 strict-ready evidence 不足 | 刷新 strict gap 连接并验证 freshness |
| `blocking` | 仍阻断一个或多个项目 | 进入项目或 monitor 修复失败源 |
| `stale_or_unknown` | 证据过期或状态不可判定 | 重新拉取 provider evidence |
| `none` | 当前 provider 证据链达标 | 保持定时 smoke 与 freshness 检查 |

该能力解决的问题：

- 不再只看 provider 是否配置，而是看真实证据是否存在、是否新鲜、是否能通过 strict gate。
- 每个 provider 都能明确输出下一步动作，减少人工排查成本。

### 3.3 视觉农场生产化缺口诊断

增强的接口：

- `GET /api/visual-farm/status`

新增字段：

- `readinessGapType`
- `readinessGapSummary`
- `remediationAction`
- `remediationActionPath`
- `remediationActionLabel`
- `acceptanceGateId`

缺口类型：

| 类型 | 含义 | 处理建议 |
| --- | --- | --- |
| `missing_endpoint` | 未配置 visual farm endpoint | 配置至少一个 endpoint 后重新 probe |
| `missing_token` | 缺少访问 token | 配置 visual farm 凭证 |
| `missing_probe` | 尚无 probe 历史 | 执行 visual farm probe |
| `stale_probe` | probe 已过 freshness 窗口 | 重新执行 probe |
| `blocking_probe` | 最新 probe 有阻断 endpoint | 修复 endpoint 后再次 probe |
| `run_failures` | 最近 visual regression run 有失败、fallback、未配置或 strict blocked case | 复查 run 并清理 artifact/provider 缺口 |
| `strict_not_enabled` | strict 模式未启用 | 生产发布前启用 strict visual farm gate |
| `none` | visual farm strict publish ready | 继续保持发布前 probe 新鲜 |

该能力解决的问题：

- 视觉回归不再只展示 run 结果，而是能判断 visual farm 本身是否可作为生产发布 gate。
- 验收逻辑能区分 endpoint、token、probe、run failure、strict mode 等不同原因。

### 3.4 验收页统一展示

增强页面：

- `apps/web/app/acceptance/page.tsx`
- 前端路径：`/acceptance`

页面现在汇总：

- 验收 gate 总览。
- 当前失败 gate。
- remaining blocking tasks。
- provider evidence gaps。
- visual farm readiness gaps。
- product benchmark workflow stages。
- 每项能力的 weakest stage。

该页面是当前项目最重要的“上线前健康页”。如果用户只看一个页面，应优先看 `/acceptance`。

## 4. 关键验收 Gate

当前重点 gate 包括：

| Gate ID | 目的 | 通过条件概述 |
| --- | --- | --- |
| `real_provider_samples` | 防止 provider 伪配置 | read/write real evidence 数量与 freshness 达标 |
| `market_evidence_freshness` | 防止趋势/新闻/问答源过期 | trend/news/qa connected 且 fresh |
| `market_workspace_readiness` | 防止单项目掩盖全局退化 | workspace strict-ready 项目数达标 |
| `visual_farm_runtime_ready` | 防止视觉农场不可用仍发布 | endpoint、token、fresh probe、connected、无 blocking、run clean |
| `runtime_architecture_production` | 防止运行时队列/Redis 假可用 | worker/queue/Redis/db 健康检查达标 |
| `mvp_ad_recommendations` | 防止广告建议缺真实证据 | ad audit 和 ad network evidence 达标 |

## 7. 后续优先级建议

### P0：继续扩大真实 Provider 样本

优先接通真实 Search Console、GA4、GitHub、CMS、Script、ad network、trend/news/qa provider。目标是减少 `missing_real`、`fallback_only` 和 `strict_gap`。

### P0：视觉农场真实端点与失败闭环

为 visual farm 配置真实 endpoint/token，跑通 probe history、visual regression run、artifact 下载和 strict publish gate。

### P1：Runtime Edge 生产流量验证

补真实 host/path rewrite、canary rollout、probe history、rollback drill，避免 runtime route 只停留在策略和导出层。

### P1：广告 reporting 与结算联动

补更多真实广告平台 reporting contract，将 RPM/eCPM/settlement window/abnormal revenue 与 settlement execution 对齐。

### P2：实验治理指标闭环

补 assignment history、guardrail metric、自动停止条件和 runtime rollback 联动。

## 8. 后续 Agent 接手提示

如果继续完善项目，建议按以下顺序工作：

1. 先打开 `/acceptance` 看失败 gate 和 provider/visual gap。
2. 再查 `GET /api/product-benchmark` 确认能力最弱阶段。
3. 优先处理 `blocking=true` 的 remaining task。
4. 每次补功能时同步更新：API model、service、contract、fallback、前端页面、smoke test。
5. 每次提交前运行 typecheck 和标准测试。

不要只新增文档或静态 UI；每个生产化能力都应至少具备：状态字段、缺口类型、修复动作、验收 gate、测试覆盖。
